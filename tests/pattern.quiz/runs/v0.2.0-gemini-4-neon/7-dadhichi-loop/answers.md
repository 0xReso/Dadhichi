**Q1**
**Why:** 1. Under startup work selection, the round reads `loop/STATE.md` first and checks whether it names an unfinished step. 2. `loop/STATE.md` names `Run test set B for pattern-a`. 3. Because an unfinished step exists, the agent must finish it before picking any new item from `loop/BACKLOG.md` (a backlog is the ordered list of work items).
**Answer:** `Run test set B for pattern-a`.
**The trap:** Choosing `Item 3: Write pattern-c` from believing the first open `[ ]` item in `loop/BACKLOG.md` always starts the round, or choosing `Item 2` by treating `[~]` as open work.
**Rule:** Always finish an unfinished step named in `loop/STATE.md` before taking a new `[ ]` item from `loop/BACKLOG.md`.

**Q2**
**Why:** 1. Under frozen prompt snapshots, the agent must save an exact copy of the prompt as `prompt.md` inside the run folder (`runs/r1/prompt.md`) before executing tests, so later edits cannot alter the record of what ran. 2. Under isolated test subagents (a subagent is an independent agent instance with clean context), test outputs must be generated by fresh general-purpose subagents given only the prompt with its inputs filled in, never builder notes or opinions.
**Answer:** (a)
**The trap:** (b) assumes extra notes help test subagents stay accurate, contaminating the evidence; (c) treats freezing after a run as equivalent to freezing beforehand; (d) assumes the builder can run tests itself.
**Rule:** Freeze `prompt.md` in the run folder before running, and pass fresh subagents only the filled-in prompt.

**Q3**
**Why:** 1. Under builder-judge separation, the round agent builds and edits while `dadhichi-head` (a separate agent running a different model) performs all reviews and grades. 2. The builder must never grade its own outputs, regardless of how obvious a failure looks. 3. The builder passes file paths and a target review output path to `dadhichi-head` so it inspects the raw artifacts and writes the grade directly.
**Answer:** (b)
**The trap:** (a) assumes obvious failures justify self-grading to save time; (c) filters raw evidence through builder summaries; (d) substitutes a same-model subagent for the separate-model `dadhichi-head` judge.
**Rule:** Never grade your own outputs—always hand file paths and an output review path to `dadhichi-head`.

**Q4**
**Why:** 1. Under the strict promotion gate, promoting a new version requires two conditions verified by `dadhichi-head`: it must pass more checks than the released version, and it must fail none that the old version passed (zero regressions, where a regression is a previously passing check turning into a failure). 2. `v1.1` passes 4 checks versus `v1.0`'s 2, meeting the first condition. 3. However, `v1.0` passed `C2` and `v1.1` failed `C2`, violating the zero-regression condition.
**Answer:** `No — C2.`
**The trap:** Answering `Yes` from believing a higher overall score (4/5 vs 2/5) outweighs losing a single earlier pass.
**Rule:** A new version can be promoted only if it passes strictly more checks and regresses on none the old version passed.

**Q5**
**Why:** 1. Under the end-of-round commit workflow, every round commits its changes using `git add -A` followed by `git commit -m "<summary>"`, so commands 1 and 2 are required. 2. Under session-dependent git push, on a local Mac the external runner script (the host wrapper that launches rounds) handles `git push` automatically. 3. Therefore the agent must not run command 3.
**Answer:** `3` (`git push`).
**The trap:** Assuming every local commit must be pushed by the agent immediately, or thinking `git add -A` is unsafe and skipping command 1.
**Rule:** Always stage with `git add -A` and commit, but leave `git push` to the runner script on a Mac.

**Q6**
**Why:** 1. Under terminal status signaling, every round must end with an exact `DADHICHI-STATUS:` line. 2. `DADHICHI-STATUS: IDLE` is allowed only when zero `[ ]` items remain in `loop/BACKLOG.md`. 3. After finishing Item 1, Item 3 is still marked `[ ]` and no human blocker occurred, so work remains for the next round.
**Answer:** `DADHICHI-STATUS: CONTINUE`
**The trap:** Outputting `DADHICHI-STATUS: IDLE` because the current round's item finished, or adding extra prose after the status line.
**Rule:** End with `DADHICHI-STATUS: CONTINUE` whenever at least one `[ ]` item remains and no blocker stops progress.

**Q7**
**Why:** 1. Under unattended autonomy, nobody is watching the round, so the agent cannot stop to ask questions. 2. When facing a non-blocking choice, the agent makes the sensible choice, records why, and keeps going. 3. Under stateless file handoff, the next round has no memory of this conversation, so decisions for user review must be written to files—specifically `loop/STATE.md`—not left only in chat.
**Answer:** (b)
**The trap:** (a) treats routine design ambiguity as a human blocker; (c) assumes chat replies persist across rounds; (d) avoids deciding and leaves work uncommitted.
**Rule:** In an unattended round, make the sensible choice, document it in files for review, and keep moving.

**Q8**
**Why:** 1. Under the startup reading order, the round reads `loop/STATE.md` (E) first to check for unfinished work. 2. Second, it reads `loop/BACKLOG.md` (C) to see the work list. 3. Third, it reads `Dadhichi Master Prompt Library System Design.md` (B) so it knows library rules before changing any prompt. 4. Fourth, it reads `CHANGELOG.md` (A) and the files the current item touches (`patterns/p1/prompt.md`, D) together at step 4.
**Answer:** `E, C, B, (A, D)`
**The trap:** Opening the target prompt file (D) or the System Design doc (B) before checking `STATE.md` and `BACKLOG.md`, or reading `CHANGELOG.md` before System Design.
**Rule:** Read `STATE.md`, then `BACKLOG.md`, then the System Design doc, and only then `CHANGELOG.md` and touched files.

**Q9**
**Why:** 1. Under completion ticking, a backlog item is ticked `[x]` only when the whole item is finished. 2. Because the agent split `Build pattern-c` into three sub-items and finished only sub-item 1, sub-item 1 is complete (`[x]`) while sub-items 2 and 3 remain open (`[ ]`). 3. Because the parent item is not fully done, the parent remains `[ ]` rather than `[x]` or `[~]`.
**Answer:** (b)
**The trap:** (a) ticks the parent `[x]` after partial progress; (c) misuses `[~]` to mean "in progress," which would cause later rounds to skip it; (d) leaves completed sub-item 1 unticked.
**Rule:** Tick `[x]` only when an entire item is done; keep a split parent `[ ]` until every sub-item under it is complete.

**Q10**
**Why:** 1. Under one-line failure logging, every failure goes into that pattern's `failures.md`, one line each. 2. In `runs/r1/`, Case 1 passed (0 lines) while Cases 2, 3, and 4 failed (3 failures = 3 new lines). 3. Unlike `loop/STATE.md`, `failures.md` is an accumulating log rather than overwritten each round, so adding 3 lines to the 2 existing lines yields 5 lines.
**Answer:** `5` lines.
**The trap:** Answering `3` from overwriting `failures.md` each run or combining the run into one summary line, or answering more than `5` by writing multi-line blocks per failure.
**Rule:** Append exactly one line to the pattern's `failures.md` for every individual failure, preserving earlier lines.

**Q11**
**Why:** 1. Under version immutability, a released version is never edited—even for a minor typo—so `v1.0` must stay untouched and the fix must go into a new version like `v1.1`. 2. Under the strict promotion gate, a new version can be promoted only after `dadhichi-head` verifies that it passes more checks than the old version and fails none the old version passed.
**Answer:** (b)
**The trap:** (a) and (c) assume small fixes or re-grading make in-place edits of released versions acceptable; (d) skips the promotion gate for "obviously safe" edits.
**Rule:** Never edit a released version—put every fix in a new version and promote only after `dadhichi-head` verifies strict improvement.

**Q12**
**Why:** 1. Under session-dependent git push, the commit step (`git add -A` then `git commit`) is required in every environment, but pushing depends on whether a runner script exists. 2. In a cloud session (no runner), the agent itself must push the commit to the session's branch at the end, so `git push` is missing. 3. On a local Mac, the runner script handles `git push`, so the agent omits it there.
**Answer:** Missing: pushing the commit to the session's branch (`git push`). On a local Mac with the runner script, nothing is missing because the runner handles `git push`.
**The trap:** Overgeneralizing the Mac rule ("never push") to cloud sessions, or assuming both environments require the agent to push.
**Rule:** Push your commit to the session's branch in a cloud session, and omit `git push` when the Mac runner handles it.

**Q13**
**Why:** 1. Under work selection, the round checks `loop/STATE.md` first; it names no unfinished step (`None`), so the agent moves to `loop/BACKLOG.md`. 2. Scanning top to bottom, it skips `[x]` (Item 1) and skips `[~]` (Items 2 and 3). 3. It selects the first item marked `[ ]`, which is Item 4.
**Answer:** `Item 4: Write tests for pattern-d`.
**The trap:** Picking `Item 2` from assuming `[~]` marks a paused or in-progress item that the next round should resume first.
**Rule:** When `loop/STATE.md` has no unfinished step, take the first `[ ]` item in `loop/BACKLOG.md` and skip every `[~]` and `[x]`.

**Q14**

Input 1 uses fictional placeholder names (`Acme Corp`) and Input 4 uses a public-domain recipe—neither breaks a rule. 3. Input 2 invents a quote attributed to a real CEO, and Input 3 includes a real customer's private phone number and address.
**Answer:** `Input 2` (invents a quote) and `Input 3` (uses a real person's private data).

**Q15**
**Why:** 1. Step 1 properly freezes `prompt.md` beforehand, Step 2 fills inputs, and Step 4 saves the output. 2. Under isolated test subagents, fresh general-purpose subagents must receive only the prompt with its inputs filled in—never the builder's notes, hints, or opinions. 3. Step 3 leaks a coaching hint about a past failure, so a passing output no longer proves the prompt itself works.
**Answer:** Step `3` — it passes a builder hint alongside the filled-in prompt, breaking subagent isolation.

**Rule:** Give test subagents only the filled-in prompt—any extra hint or note invalidates the test evidence.

**Q16**
**Why:** 1. Under terminal status signaling, `DADHICHI-STATUS: IDLE` is used when no `[ ]` items are left in `loop/BACKLOG.md`. 2. Under work selection, `[~]` items are skipped just like `[x]` items and are never picked up automatically. 3. Here Items 1 and 3 are `[x]`, Item 2 is `[~]`, and `loop/STATE.md` has no unfinished step, so zero `[ ]` items remain.
**Answer:** `DADHICHI-STATUS: IDLE`
**The trap:** Outputting `DADHICHI-STATUS: CONTINUE` from thinking `[~]` still counts as active work, or `BLOCKED` because Item 2 is parked.
**Rule:** Emit `DADHICHI-STATUS: IDLE` when no `[ ]` items remain—skipped `[~]` items do not keep the loop running.

**Q17**
**Why:** 1. Under stateless file handoff, the end-of-round checklist requires overwriting `loop/STATE.md` with the current date/time, item, finished work, exact next step, and decisions for review. 2. Round 4 appended instead of overwriting, leaving Round 3's `Next step` intact. 3. Because Round 5 starts with no memory and obeys the unfinished step in `STATE.md`, it can pick up Round 3's stale step and re-run test set A.
**Answer:** (a)

**Q18**

**Q20**

**Q21**

**Q22**
**Why:** 1. Under work selection, the round executes the unfinished step from `loop/STATE.md` (running the 5 tests). 2. Under bounded step sizing and completion ticking, saving the 5 test outputs is a solid 50-minute step, but grading remains, so Item 2 is not wholly done and stays `[ ]`. 3. Under terminal status signaling, because Item 2 is still `[ ]`, at least one `[ ]` item remains, requiring `CONTINUE`.
**Answer:** (1) `[ ]`; (2) `DADHICHI-STATUS: CONTINUE`.
**The trap:** Ticking Item 2 `[x]` because the `STATE.md` step finished, which leaves zero `[ ]` items and causes a premature `DADHICHI-STATUS: IDLE` before grading runs.
**Rule:** Finishing one step of an item leaves the item `[ ]` and keeps the status at `CONTINUE` until the entire item is complete.

**Q23**
**Why:** 1. `patterns/p1/v1.0.md` is already released; editing it directly in Step 3 violates version immutability, which requires every fix to become a new version. 2. `runs/v1.0-check/prompt.md` was frozen before running; modifying it after Test 1 violates frozen prompt snapshots and corrupts the run so Test 1 and Tests 2–3 no longer test the same prompt.
**Answer:** (1) Version immutability (editing a released version instead of creating a new one); (2) Frozen prompt snapshots (modifying `prompt.md` after the run started).
**The trap:** Catching only the released-version edit while thinking updating `runs/v1.0-check/prompt.md` usefully keeps the run folder in sync.
**Rule:** Never edit a released version or a frozen run `prompt.md`—put fixes in a new version and start a new run folder.

**Q24**
**Why:** 1. Under builder-judge separation, `dadhichi-head` judges and the builder never grades or overrides grades, so overriding C3 is forbidden (`No`). 2. Under the strict promotion gate, with C3 failed (`v2.0` passed C3), `v2.1` regressed, so promotion is forbidden (`No`). 3. Under one-line failure logging, every failure goes into `patterns/pattern-c/failures.md` one line each—even on an unpromoted version—so skipping C3 is forbidden (`No`).
**Answer:** (1) `No`; (2) `No`; (3) `No`.
**The trap:** Thinking the builder can overrule one "harsh" grade to unlock promotion, or thinking failures on rejected versions don't belong in `failures.md`.
**Rule:** Accept `dadhichi-head`'s grades without override, block promotion on any regression, and log every failure in `failures.md`.

**Q25**
**Why:** 1. In Situation X, unattended autonomy applies: nobody is watching, the System Design permits either table size, so the agent chooses sensibly, records why, and emits `CONTINUE`. 2. In Situation Y, the agent cannot fix external credentials (project boundaries) and cannot self-grade (builder-judge separation), leaving a genuine human blocker that requires `DADHICHI-STATUS: BLOCKED <one-sentence reason>`.
**Answer:** (a)
**The trap:** (b) blocks on a routine choice the agent should make itself; (c) confuses a blocked backlog with an empty backlog (`IDLE`); (d) breaks builder-judge separation to avoid blocking.

**Q26**
**Why:** 1. Under bounded step sizing, stopping cleanly at 45 minutes with saved state beats risking a cutoff mid-run. 2. Following the end-of-round checklist in order: first add the `CHANGELOG.md` line (C), then overwrite `loop/STATE.md` with the handoff fields (B), then stage and commit all changes with `git add -A` and `git commit` (D). 3. Because this is a cloud session (no runner), push the commit (A). 4. Finally, end with `DADHICHI-STATUS: CONTINUE` (E).
**Answer:** `C, B, D, A, E`
**The trap:** Running `D` (commit) before `B` or `C` so handoff files stay uncommitted, skipping `A` in a cloud session, or putting `E` before `A`.
**Rule:** Update `CHANGELOG.md` and `loop/STATE.md` before committing, push after committing in cloud sessions, and emit the status line last.

**Q27**

**Q30**
